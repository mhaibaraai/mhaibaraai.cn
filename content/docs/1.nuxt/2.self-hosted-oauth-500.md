## 三种根因速查表

三次报错都发生在同一回调路径，但成因完全独立——先对照日志证据定位，再采取对应修复：

| 现象特征 | 根因 | 关键证据 | 对应章节 |
|---|---|---|---|
| nginx 返回 500，应用日志**无**异常堆栈 | 容器出海请求 GitHub 挂起，被 nginx 超时掐断 | nginx 日志：`upstream timed out (110: Connection timed out)`，路径 `/auth/github?code=...` | [出海请求超时：容器访问 GitHub 挂起](#出海请求超时容器访问-github-挂起) |
| 应用日志报 `ECONNREFUSED 127.0.0.1:5432` | 数据库连接串在构建期被固化成字面量 | `docker logs`：`connect ECONNREFUSED 127.0.0.1:5432` | [连接串在构建期被固化成字面量](#连接串在构建期被固化成字面量) |
| 应用日志报 `EAI_AGAIN postgres` | 应用与数据库不在同一个 Docker 网络 | `docker logs`：`getaddrinfo EAI_AGAIN postgres` | [跨 Docker 网络 DNS 解析失败](#跨-docker-网络-dns-解析失败) |

## 出海请求超时：容器访问 GitHub 挂起

### 现象与根因

`defineOAuthGitHubEventHandler` 的令牌交换与用户信息拉取发生在 `nuxt-auth-utils` 内部（依次请求 `github.com/login/oauth/access_token` 和 `api.github.com/user`）。境内服务器出海链路常出现 TCP 握手成功但 HTTPS 请求挂起，最终触发 nginx `proxy_read_timeout` 返回 500。

::warning
因为是被动超时断开，`onError` 往往来不及执行，应用日志里看不到异常。诊断依据是 nginx 日志中的 `upstream timed out (110: Connection timed out) while reading response header from upstream`。
::

### 修复：让容器出站请求走代理

Node 22 的全局 `fetch` 与 `ofetch` 不会自动读取 `HTTP_PROXY`/`HTTPS_PROXY`，需用 `undici` 的 `EnvHttpProxyAgent` 接管全局 dispatcher：

```sh [sh]
pnpm add undici
```

```ts [server/plugins/proxy.ts]
import { EnvHttpProxyAgent, setGlobalDispatcher } from 'undici'

export default defineNitroPlugin(() => {
  if (!process.env.HTTPS_PROXY && !process.env.HTTP_PROXY)
    return

  setGlobalDispatcher(new EnvHttpProxyAgent({
    headersTimeout: 10_000,
    bodyTimeout: 10_000
  }))
})
```

- 显式设置 `headersTimeout`/`bodyTimeout` 为 10 秒：即使代理偶发异常，也能快速失败进入 `onError`，避免拖到 nginx 500。
- 未配置代理环境变量时直接返回，不影响本地 `pnpm dev`；`postgres` 原生 TCP/TLS 连接不走 undici，不受影响。

### 宿主机与 Compose 侧配合

::note
给 **Docker daemon** 配置的代理（`docker.service.d/http-proxy.conf`）只作用于 `docker pull/build`，不会让运行中的容器流量走代理。
::

1. **代理客户端放行容器网段**：mihomo 等客户端默认 `allow-lan: false`（仅监听 `127.0.0.1`），需改为 `true` 并通过防火墙仅允许 Docker 网桥子网访问代理端口，禁止公网入站。
2. **Compose 注入宿主机映射与环境变量**：

   ```yaml [docker-compose.yml]
   services:
     app:
       extra_hosts:
         - "host.docker.internal:host-gateway"
       environment:
         - HTTPS_PROXY=http://host.docker.internal:7893
   ```

::tip
若代理按域名分流（如 `DOMAIN-SUFFIX,github.com`），记得同时覆盖 `ghcr.io` 与 `pkg-containers.githubusercontent.com`。放弃宿主机 iptables 透明代理方案是因为容器重建后 IP 漂移、与 Docker NAT 规则冲突且排查困难，显式 `HTTPS_PROXY` 更可控。
::

### 验证

```sh [sh]
docker exec <container> sh -c 'echo $HTTPS_PROXY'
```

重新走一遍 GitHub 登录，确认 `/auth/github` 正常回调且 nginx 无超时记录。

## 连接串在构建期被固化成字面量

### 现象与根因

应用日志明确抛出 `ECONNREFUSED 127.0.0.1:5432`，说明 GitHub 令牌交换已成功，失败在 `onSuccess` 查库阶段——运行时 `docker-compose.yml` 传入的 `DATABASE_URL` 完全未生效。

`@nuxthub/core` 在 `postgres-js`、非 dev、非 Cloudflare 托管模式下，会在 `nuxt build` 期间读取 `POSTGRES_URL`/`POSTGRESQL_URL`/`DATABASE_URL`。若构建期非空，会把值作为**字符串字面量**写死进 `.output/server` 的 `hub:db` 模块。若 CI 在 `pnpm build` 前通过 SSH 隧道跑迁移并把 `127.0.0.1:5432` 设在构建环境中，就会将临时隧道地址永久烧进产物。

### 修复与验证

将「数据库迁移」与「应用构建」彻底拆开，确保 `Build` 步骤不注入任何数据库连接串：

```yaml [.github/workflows/deploy.yml]
- name: Run database migrations
  env:
    DATABASE_URL: postgresql://${{ secrets.DB_USER }}:${{ secrets.DB_PASSWORD }}@127.0.0.1:5432/${{ secrets.DB_NAME }}
  run: pnpm db:migrate

- name: Build
  env:
    NUXT_SESSION_PASSWORD: ${{ secrets.NUXT_SESSION_PASSWORD }}
  run: pnpm build
```

::tip
本地验证时避免被 `.env` 污染，可执行 `nuxi build --dotenv=/nonexistent` 模拟干净 CI 环境，再确认产物中保留了 `process.env.DATABASE_URL` 运行时读取逻辑。
::

## 跨 Docker 网络 DNS 解析失败

### 现象与根因

连接串已在运行时正确读取，但容器日志报 `getaddrinfo EAI_AGAIN postgres`。通过 `docker inspect <name> --format '{{json .NetworkSettings.Networks}}'` 检查可见应用容器（如 `webnet`）与数据库容器（如 `database_default`）分属不同用户自定义网络——Docker 内置 DNS 仅在同一自定义网络内生效，跨网络无法解析容器名。

### 修复与验证

在应用服务的 `docker-compose.yml` 中声明并加入数据库所在外部网络（仅需改动访问数据库的服务）：

```yaml [docker-compose.yml]
services:
  movk-studio:
    networks:
      - webnet
      - database_default

networks:
  webnet:
    external: true
  database_default:
    external: true
```

重建应用容器 `docker compose up -d movk-studio` 后验证（若想不重启临时测试，可先执行 `docker network connect database_default movk-studio`，但重建后会失效）：

```sh [sh]
docker exec movk-studio getent hosts postgres
```

确认解析出内网 IP 后，重新触发 GitHub 登录验证无 `ECONNREFUSED` / `EAI_AGAIN` 报错。
